## 2. Функція SMS-повідомлень (encrypted DMR SMS)

**Статус:** код повністю готовий (UI: Home/List/Read/Compose/Recipient/Result, повне API в
`dmr_sms.h`, сховище у SPI-flash, шифрування AES-256-ECB підтверджене на реальному стоковому TYT
за коментарем у шапці `dmr_sms.c`), але вимкнений прапорцем `ENABLE_DMR_DATA` (за замовчуванням
`0`, ніде не вмикається жодним build-скриптом/CI). `dmr_data.c` (шар keying data-виклику) сам себе
називає "harness (Phase 2)" — останній коміт 2026-07-05, після цього жодного разу не збирався
разом з рештою дерева.

**План:**
1. Зібрати тестову прошивку: `make ENABLE_AES=1 ENABLE_DMR_DATA=1`.
2. Прошити на робочу рацію, перевірити повний цикл: Compose → Send (зашифроване й відкритим
   текстом) → прийом на стоковій TYT і навпаки; Inbox/Sent, непрочитані, видалення.
3. Якщо стабільно — вирішити, чи вмикати `ENABLE_DMR_DATA=1` за замовчуванням у наших збірках, чи
   лишити опційним прапорцем.
4. Прибрати мертву гілку `-3` в `menuMessages.c` заразом.

## 3. Ідея: віддалене керування рацією в мережі (у розробці — ядро написане й перевірене)

Розглянуті три можливості:

- **Перевірка доступності станції ("radio check")** — найпростіше й найнижчий ризик технічно.
  Легкий poll/ack поверх вже наявного CSBK-led data-каналу (той самий механізм, що й SMS).
  Працюватиме лише між раціями на цій прошивці (не сумісно зі стоковими без реверс-інжинірингу
  їхнього протоколу).
- **Віддалене прослуховування ("remote monitor")** — технічно можливе (в коді вже є повний
  стан приватного виклику `uiDataGlobal.PrivateCall` з accept/decline в `uiPrivateCall.c`), але
  потребує обходу поточного UI-підтвердження виклику заради автоматичної безмовної відповіді.
  Це чутлива функція: приховане ввімкнення мікрофона без відома оператора — по суті засіб
  прихованого прослуховування. Погоджуся допомагати лише з версією "тільки власний флот":
  цільова рація повинна заздалегідь дати згоду/налаштувати білий список ID, які можуть її
  прослуховувати, і мати непримусовий локальний індикатор (іконка/LED), який не можна вимкнути.
  НЕ буду допомагати реверс-інжинірити реальний фірмовий протокол Motorola/Hytera/TYT для
  сумісності — це дало б змогу прошивці прослуховувати чужі, не власні, комерційні рації без
  згоди їх власників, що є інструментом стеження проти третіх осіб.
- **Дистанційне блокування/розблокування ("stun/kill/revive")** — та сама логіка: версія
  "тільки власний флот" (наприклад, деактивувати власну вкрадену рацію) — розумна й корисна
  функція, готовий допомагати. Версія, сумісна з реальним фірмовим протоколом стокових/чужих
  рацій (тобто здатна заблокувати БУДЬ-яку сумісну комерційну рацію в ефірі без згоди власника)
  — це фактично інструмент відмови в обслуговуванні/зловмисного виведення з ладу чужого
  обладнання; таку сумісність будувати не буду.

### Модель довіри (узгоджено 2026-08-31)

- **Ключ:** той самий AES-ключ каналу, що й голос (окремого "адмін"-ключа поки не заводимо —
  простіше на старті; якщо з'явиться потреба в окремій ролі "хто керує" від "хто чує", можна
  додати окремий слот ключа пізніше без зміни формату команди).
- **Приймання команд:** вимкнено за замовчуванням на кожній рації. Потрібен явний opt-in —
  окремий прапорець у custom-data (за зразком того, як зараз зберігаються ключі й пресети SMS),
  плюс опційний білий список ID, яким дозволено видавати команди. Налаштовується поки лише через
  хост-утиліту по USB (аналог `aes_key_store.py`), бо власного меню на рації для цього ще нема.

### Формат команди керування (спільний для всіх трьох підфункцій) — РЕАЛІЗОВАНО й перевірено

16-байтовий PDU (рівно один блок AES-256-ECB — не треба логіки доповнення/padding), зашифрований
тим самим ключем каналу, що й голос. Сам CSBK-led data TX/RX (той самий механізм, що й SMS/
`dmr_data.c`) поки НЕ підключений — див. "Що зроблено" нижче.

```
байт 0-1:   магічна мітка 'R','C' (швидка перевірка, що ключ підійшов і розшифрував не сміття)
байт 2:     тип команди (1=CHECK_REQ, 2=CHECK_ACK, 3=MONITOR_START, 4=MONITOR_STOP, 5=STUN, 6=REVIVE)
байт 3:     зарезервовано (0)
байти 4-7:  DMR ID видавця команди (little-endian)
байти 8-11: монотонний лічильник видавця (little-endian) — захист від replay
байти 12-15: корисне навантаження, залежне від типу команди (напр. заряд/RSSI в CHECK_ACK)
```

**Захист від replay:** приймач тримає для кожного дозволеного ID останній прийнятий лічильник
(окрема таблиця, скидається при перезавантаженні); команда приймається лише якщо `seq` строго
більший за останній прийнятий для цього ID — інакше відкидається, а лічильник НЕ змінюється (щоб
відхилена/повторена спроба не могла збити відлік справжньому видавцю).

**Допуск:** свідомо НЕ "порожній білий список = дозволити всім із правильним ключем" — сам факт, що
хтось підібрав ключ шифрування, недостатній доказ права видавати команди керування (на відміну від
голосу/SMS, де мета — просто зв'язок, а не примусова дія над чужою рацією). `enabled=1` без жодного
налаштованого ID означає "увімкнено, але нікому конкретно ще не довіряю" — команди все одно
відкидаються, поки список не заповнений.

### Перевірка доступності ("radio check")

Найпростіше й найнижчий ризик. Запит → якщо ціль дозволила приймання команд і ID видавця в білому
списку (якщо він заданий) → одразу ack-відповідь (свій ID, опційно заряд/RSSI). Без жодної взаємодії
з оператором цілі.

### Віддалене прослуховування ("remote monitor")

Команда "monitor-start" на дозволеній рації: примусово вмикає TX з мікрофоном на **жорстко обмежений
час** (наприклад 30-60 с, автозавершення), в обхід звичайного UI-підтвердження приватного виклику
(`uiPrivateCall.c`) — але **лише** для цього типу команди й лише від ID з білого списку. Обов'язковий
**незнімний** локальний індикатор на екрані/LED, поки триває трансляція — не вимикається програмно
навіть на прохання видавця команди; це запобіжник проти зловживання навіть власником іншої рації в
тому самому флоті. "monitor-stop" (або сплив таймера) одразу вимикає TX.

### Блокування / розблокування ("stun" / "revive")

"stun" — постійний прапорець у custom-data (переживає перезавантаження, як ключі), що блокує TX
голосу й даних, **крім** самого каналу керування — рація має й далі слухати команди керування,
інакше "revive" стане неможливим. "revive" знімає прапорець.

Свідомо **не** реалізовуємо незворотний "kill" на цьому етапі — ризик випадкового чи зловмисного
назавжди виведення рації з ладу переважує користь; якщо колись знадобиться, це окреме
обговорення з користувачем.

**Наступний крок:** написати блок конфігурації "RCTL" (custom-data) і підключити PDU до реального
TX/RX — але це вже краще робити з компілятором під рукою (ПК), а не наосліп із телефону, саме через
ISR-код у `HR-C6000.c`, який неможливо перевірити без збірки.

## 4. Спроба збірки прямо на телефоні через Termux (2026-08-31, висновок: залишили ПК/CI)

Редагування коду й `git`/SSH-push з Termux працюють повністю (перевірено на практиці — коміт
`d93a3df` зроблено й запушено прямо з телефону). Повна компіляція прошивки на телефоні — ні, з двох
незалежних причин, обидві варто пам'ятати, якщо колись повертатись до ідеї:

- `tools/codec_cleaner.Linux` (потрібен наприкінці `make` для підготовки області кодека) — це
  готовий x86-64 ELF-бінарник без вихідного коду в цьому дереві; на ARM64-телефоні не запуститься
  за визначенням, незалежно від тулчейну.
- Офіційний тулчейн ARM GNU (навіть aarch64-hosted збірка, яка мала б підійти під ARM64-телефон)
  лінкований проти glibc й шукає системний завантажувач за шляхом, якого немає в Termux (там немає
  стандартної структури `/lib`, `/usr` — усе під власним префіксом). Розпакувати вдалось (обхідним
  шляхом через Python-скрипт, бо `tar` не може створювати жорсткі посилання під Android), але
  виконати бінарники — ні (`required file not found`).
- Стандартне рішення — `proot-distro install ubuntu` (повноцінний Ubuntu-контейнер у Termux) — свідомо
  відклали: зайвий шар складності заради "приємного, але не обов'язкового" на цьому етапі.
- Компіляцію в моєму (Claude) хмарному середовищі теж не вдалось перевірити як запасний варіант:
  мережева політика організації блокує і `archive.ubuntu.com`, і `developer.arm.com`.

Висновок: Termux = редагування коду + git (повністю робочий цикл). Компіляція й прошивка — ПК/CI,
як і раніше.
