## 3. Ідея: віддалене керування рацією в мережі (у розробці — ядро написане й перевірене)

Розглянуті три можливості:

- **Перевірка доступності станції ("radio check")** — найпростіше й найнижчий ризик технічно.
  Легкий poll/ack поверх вже наявного CSBK-led data-каналу (той самий механізм, що й SMS).
  Працюватиме лише між раціями на цій прошивці (не сумісно зі стоковими без реверс-інжинірингу
  їхнього протоколу).
- **Віддалене прослуховування ("remote monitor")** — технічно можливе (в коді вже є повний
  стан приватного виклику `uiDataGlobal.PrivateCall` з accept/decline в `uiPrivateCall.c`), але
  потребує обходу поточного UI-підтвердження виклику заради автоматичної безмовної відповіді.
  Це чутлива функція: приховане ввімкнення мікрофона без відома оператора — по суті засіб
  прихованого прослуховування. Погоджуся допомагати лише з версією "тільки власний флот":
  цільова рація повинна заздалегідь дати згоду/налаштувати білий список ID, які можуть її
  прослуховувати, і мати непримусовий локальний індикатор (іконка/LED), який не можна вимкнути.
  НЕ буду допомагати реверс-інжинірити реальний фірмовий протокол Motorola/Hytera/TYT для
  сумісності — це дало б змогу прошивці прослуховувати чужі, не власні, комерційні рації без
  згоди їх власників, що є інструментом стеження проти третіх осіб.
- **Дистанційне блокування/розблокування ("stun/kill/revive")** — та сама логіка: версія
  "тільки власний флот" (наприклад, деактивувати власну вкрадену рацію) — розумна й корисна
  функція, готовий допомагати. Версія, сумісна з реальним фірмовим протоколом стокових/чужих
  рацій (тобто здатна заблокувати БУДЬ-яку сумісну комерційну рацію в ефірі без згоди власника)
  — це фактично інструмент відмови в обслуговуванні/зловмисного виведення з ладу чужого
  обладнання; таку сумісність будувати не буду.

### Модель довіри (узгоджено 2026-08-31)

- **Ключ:** той самий AES-ключ каналу, що й голос (окремого "адмін"-ключа поки не заводимо —
  простіше на старті; якщо з'явиться потреба в окремій ролі "хто керує" від "хто чує", можна
  додати окремий слот ключа пізніше без зміни формату команди).
- **Приймання команд:** вимкнено за замовчуванням на кожній рації. Потрібен явний opt-in —
  окремий прапорець у custom-data (за зразком того, як зараз зберігаються ключі й пресети SMS),
  плюс опційний білий список ID, яким дозволено видавати команди. Налаштовується поки лише через
  хост-утиліту по USB (аналог `aes_key_store.py`), бо власного меню на рації для цього ще нема.

### Формат команди керування (спільний для всіх трьох підфункцій) — РЕАЛІЗОВАНО й перевірено

16-байтовий PDU (рівно один блок AES-256-ECB — не треба логіки доповнення/padding), зашифрований
тим самим ключем каналу, що й голос. Сам CSBK-led data TX/RX (той самий механізм, що й SMS/
`dmr_data.c`) поки НЕ підключений — див. "Що зроблено" нижче.

```
байт 0-1:   магічна мітка 'R','C' (швидка перевірка, що ключ підійшов і розшифрував не сміття)
байт 2:     тип команди (1=CHECK_REQ, 2=CHECK_ACK, 3=MONITOR_START, 4=MONITOR_STOP, 5=STUN, 6=REVIVE)
байт 3:     зарезервовано (0)
байти 4-7:  DMR ID видавця команди (little-endian)
байти 8-11: монотонний лічильник видавця (little-endian) — захист від replay
байти 12-15: корисне навантаження, залежне від типу команди (напр. заряд/RSSI в CHECK_ACK)
```

**Захист від replay:** приймач тримає для кожного дозволеного ID останній прийнятий лічильник
(окрема таблиця, скидається при перезавантаженні); команда приймається лише якщо `seq` строго
більший за останній прийнятий для цього ID — інакше відкидається, а лічильник НЕ змінюється (щоб
відхилена/повторена спроба не могла збити відлік справжньому видавцю).

**Допуск:** свідомо НЕ "порожній білий список = дозволити всім із правильним ключем" — сам факт, що
хтось підібрав ключ шифрування, недостатній доказ права видавати команди керування (на відміну від
голосу/SMS, де мета — просто зв'язок, а не примусова дія над чужою рацією). `enabled=1` без жодного
налаштованого ID означає "увімкнено, але нікому конкретно ще не довіряю" — команди все одно
відкидаються, поки список не заповнений.

### Перевірка доступності ("radio check")

Найпростіше й найнижчий ризик. Запит → якщо ціль дозволила приймання команд і ID видавця в білому
списку (якщо він заданий) → одразу ack-відповідь (свій ID, опційно заряд/RSSI). Без жодної взаємодії
з оператором цілі.

### Віддалене прослуховування ("remote monitor")

Команда "monitor-start" на дозволеній рації: примусово вмикає TX з мікрофоном на **жорстко обмежений
час** (наприклад 30-60 с, автозавершення), в обхід звичайного UI-підтвердження приватного виклику
(`uiPrivateCall.c`) — але **лише** для цього типу команди й лише від ID з білого списку. Обов'язковий
**незнімний** локальний індикатор на екрані/LED, поки триває трансляція — не вимикається програмно
навіть на прохання видавця команди; це запобіжник проти зловживання навіть власником іншої рації в
тому самому флоті. "monitor-stop" (або сплив таймера) одразу вимикає TX.

### Блокування / розблокування ("stun" / "revive")

"stun" — постійний прапорець у custom-data (переживає перезавантаження, як ключі), що блокує TX
голосу й даних, **крім** самого каналу керування — рація має й далі слухати команди керування,
інакше "revive" стане неможливим. "revive" знімає прапорець.

Свідомо **не** реалізовуємо незворотний "kill" на цьому етапі — ризик випадкового чи зловмисного
назавжди виведення рації з ладу переважує користь; якщо колись знадобиться, це окреме
обговорення з користувачем.

**Наступний крок:** написати блок конфігурації "RCTL" (custom-data) і підключити PDU до реального
TX/RX — але це вже краще робити з компілятором під рукою (ПК), а не наосліп із телефону, саме через
ISR-код у `HR-C6000.c`, який неможливо перевірити без збірки.

## 4. Спроба збірки прямо на телефоні через Termux (2026-08-31, висновок: залишили ПК/CI)

Редагування коду й `git`/SSH-push з Termux працюють повністю (перевірено на практиці — коміт
`d93a3df` зроблено й запушено прямо з телефону). Повна компіляція прошивки на телефоні — ні, з двох
незалежних причин, обидві варто пам'ятати, якщо колись повертатись до ідеї:

- `tools/codec_cleaner.Linux` (потрібен наприкінці `make` для підготовки області кодека) — це
  готовий x86-64 ELF-бінарник без вихідного коду в цьому дереві; на ARM64-телефоні не запуститься
  за визначенням, незалежно від тулчейну.
- Офіційний тулчейн ARM GNU (навіть aarch64-hosted збірка, яка мала б підійти під ARM64-телефон)
  лінкований проти glibc й шукає системний завантажувач за шляхом, якого немає в Termux (там немає
  стандартної структури `/lib`, `/usr` — усе під власним префіксом). Розпакувати вдалось (обхідним
  шляхом через Python-скрипт, бо `tar` не може створювати жорсткі посилання під Android), але
  виконати бінарники — ні (`required file not found`).
- Стандартне рішення — `proot-distro install ubuntu` (повноцінний Ubuntu-контейнер у Termux) — свідомо
  відклали: зайвий шар складності заради "приємного, але не обов'язкового" на цьому етапі.
- Компіляцію в моєму (Claude) хмарному середовищі теж не вдалось перевірити як запасний варіант:
  мережева політика організації блокує і `archive.ubuntu.com`, і `developer.arm.com`.

Висновок: Termux = редагування коду + git (повністю робочий цикл). Компіляція й прошивка — ПК/CI,
як і раніше.

## 5. Нотатка: як правильно порівнювати розмір збірок (2026-08-31)

При першій реальній ARM-збірці на ПК (`ENABLE_AES=0` vs `=1` vs `=1 ENABLE_DMR_DATA=1`) звичайний
`arm-none-eabi-size build/openuv380-10w.elf` (без `-A`) показував **однаковісінький** `.text` у всіх
трьох збірках, хоча лінкер точно підключав тисячі байт нового коду (SMS). Це на хвилину виглядало як
ознака, що щось не так із прапорцями чи умовами компіляції.

**Причина (не баг, а свідома конструкція цього форку):** секція `.codec_bin_section_1` —
400+ КБ заглушки замість пропрієтарного AMBE-кодека (реальний кодек не можна поширювати відкрито,
див. `tools/codec_cleaner.Linux` і `flash.sh`) — підганяється так, щоб сумарний обсяг флеш-регіону
"код + заглушка кодека" лишався фіксованим: коли `.text`/`.rodata` реального коду зростають, заглушка
рівно настільки ж меншає. Звичайний (Berkeley) формат `size` додає цю заглушку в колонку "text" разом
зі справжнім кодом — і сума виходить незмінною, маскуючи будь-яку реальну різницю.

**Правильний спосіб порівнювати:** `arm-none-eabi-size -A build/openuv380-10w.elf` (посекційно) і/або
`arm-none-eabi-nm --size-sort` + `comm` для списку символів, що з'явились/зникли між збірками — так,
як зроблено вище для перевірки SMS. Звичайний `size` без `-A` придатний лише щоб побачити, що збірка
взагалі відбулась, не для порівняння розміру між прапорцями.

**Побічно підтверджено цим самим порівнянням:** новий RCTL-модуль (`dmrRctlGate`, `dmr_rctl_pack`,
`dmr_rctl_gate_check` і решта з `dmr_rctl_cfg.c`/`dmr_rctl_pdu.c`) у списку символів фінального
`.elf` відсутній повністю — `--gc-sections` викидає його, бо його ще нізвідки не викликають. Тобто
на практиці, не лише за задумом, цей код зараз важить 0 байт у прошивці й не впливає на неї, поки
свідомо не підключений до TX/RX (пункт 3 вище).

## 6. Нотатка: fwsym.py мав захардкожений шлях (2026-08-31, коміт cf5e4af)

`tools/fwsym.py` (`--stamp`/`--check`) мав `_FW_DIR = "~/repo/MDUV380_firmware"` — жорстко зашиту
назву теки клону "repo". У будь-кого, хто клонував під іншою назвою (у нас — `OpenGD77-AES256`),
`--stamp` падав з `No such file or directory`. Виправлено на `os.environ.get("FW_DIR", ...)` —
запускати як `FW_DIR=~/OpenGD77-AES256/MDUV380_firmware python3 tools/fwsym.py --stamp`. Старий
дефолт лишили як fallback заради зворотної сумісності з тим, хто раніше клонував саме в `~/repo`.

## 7. Messages: перенесення в головне меню + UX-функції (2026-08-31, коміт 9fefe7d)

**Статус:** реально скомпільовано (`make clean && make ENABLE_AES=1 ENABLE_DMR_DATA=1`, чисто) і
прошито на робочу рацію. Пункт "Messages" в головному меню підтверджено візуально. **Функціональне
тестування (SMS, звук, пікер контактів) — заплановано на завтра, ще не зроблено.**

**Що змінено (5 файлів: `menuMessages.c`, `menuSystem.c`, `dmr_sms.c`, `sound.c`, `sound.h`):**
- `MENU_MESSAGES` перенесено з `optionsMenuItems[]` у `mainMenuItems[]` — тепер самостійний пункт
  головного меню, а не налаштування в Options (лише коли зібрано з `ENABLE_AES` + `ENABLE_DMR_DATA`).
- READ-екран: звичайний `GREEN` (без SK2) тепер Reply (Inbox: чистий текст, отримувач = відправник)
  або Resend (Sent: і текст, і отримувач попередньо заповнені, одразу на RECIPIENT) — нова функція
  `startReplyOrResend()`. Новий прапорець `s_msg.rcptPreset` не дає `composeEvent()`-у затерти
  преднабраного відправника дефолтним отримувачем.
- LIST-екран: `SK2+RED` позначає всі вхідні прочитаними одним натисканням (`dmrSmsMarkAllRead()`),
  до вже наявного `SK2+GREEN` (видалення).
- RECIPIENT-екран: новий вхід `SK1` → новий екран `MSG_PICK_CONTACT` — список контактів кодплагу
  (TG чи PC, залежно від поточного перемикача Group/Private), `GREEN` підставляє обраний контакт,
  `RED` — назад без змін. Використано стандартний `menuGetMenuOffset`/`menuDisplayEntry` ідіом
  прокрутки й API `codeplugContactsGetCount()`/`codeplugContactGetDataForNumberInType()`.
- На вхідне SMS (`dmrSmsRxTick()` у `dmr_sms.c`) додано `soundSetMelody(MELODY_SMS_RECEIVED_BEEP)` —
  раніше сповіщення було лише візуальним (банер), звуку не було зовсім.

**Перевірка без реального заліза (UI-код, host-тестів для нього нема):** повний ручний перегляд
diff'ів усіх 5 файлів; звірка балансу дужок/`#if`/`#endif`; звірка кожного виклику API кодплагу з
реальними сигнатурами в `codeplug.h`. Після реальної збірки — звірка через
`arm-none-eabi-nm --size-sort`, що новий код підключений: `pickContactUpdate`, `menuMessages`,
`MELODY_SMS_RECEIVED_BEEP` знайдені з реальними адресами. `pickContactEvent` і `startReplyOrResend`
у символах відсутні — перевірено, що це очікуваний інлайнінг (`-O2` розчиняє статичні функції з
рівно одним місцем виклику: та сама поведінка в тому ж файлі й для вже існуючих `doSend`,
`prefillRecipient`, `cyclePreset`), а не випадання коду.

**Наступний крок:** функціональний тест на рації (Inbox/Sent, Reply/Resend, mark-all-read, пікер
контактів, звук на вхідне SMS) — завтра.

## 8. Дослідження: українізація інтерфейсу (2026-08-31, лише дослідження, коду в прошивці ще нема)

Прошивка вже підтримує повну заміну шрифту й таблиці рядків меню під конкретну мову — саме так
зроблено для японської (`LANGUAGE_BUILD_JAPANESE`, окремий `HX8353E_charset_JA.h`, гілки в
`HX8353E_display.c`/`uiLocalisation.c`/`menuLanguage.c`). Український варіант — той самий, вже
перевірений архітектурний шлях (`LANGUAGE_BUILD_UKRAINIAN` + власний charset-файл + `ukrainian.h` за
зразком 18 вже наявних мов у `application/include/user_interface/languages/`), а не щось нове.

**Розібрано формат растру шрифту** (`HX8353E_charset.h`, функція `displayPrintCoreDoubleHeight` у
`HX8353E_display.c`): побайтові "стовпці" по 8 пікселів заввишки, `pixel(x,y) = (byte[x + (y/8)*width]
>> (y%8)) & 1` (біт 0 = верхній піксель стовпця). UI меню реально використовує 3 з 7 таблиць шрифту:
`font_6x8` (FONT_SIZE_1, підказки), `font_8x8` (FONT_SIZE_2, середній текст), `font_8x16` (FONT_SIZE_3,
великий текст) — саме їх треба заповнити кирилицею в першу чергу.

**Джерело гліфів 8x16 — знайдено й перевірено візуально:** GNU Unifont (ліцензія SIL OFL, вільна для
використання в прошивці) дає готові, чисті кириличні гліфи рівно 8×16 пікселів "з коробки" — перевірено
рендером усіх проблемних українських літер (Ї, Є, Ґ, Щ, Ж) через ASCII-арт і зведене PNG-прев'ю
(надіслано користувачу). Для 8x8 і 6x8 ідеального готового джерела нема — протестовано декілька
векторних шрифтів (найкращий кандидат `FreeMonoBold`, стиснутий до потрібного розміру), складні літери
(Щ, Ж, Ю) на такому дрібному растрі читаються помітно гірше, ніж уже наявний рукописний латинський
шрифт цієї рації. Користувач ще не підтвердив прийнятність якості 8x8/6x8 — рішення по цьому пункту
відкладено до відповіді.

**Другий, окремий і незалежний шматок роботи:** таблиця рядків меню `stringsTable_t`
(`uiLanguage.h`) — кожен рядок `char[LANGUAGE_TEXTS_LENGTH]`, тобто рівно 17 байт (16 видимих символів
+ нуль-термінатор). Українські переклади часто довші за англійський оригінал — доведеться агресивно
скорочувати. Хостовий інструмент `languages_builder.c` вже вміє перевіряти мовні файли на такі
переповнення — можна перевикористати замість писати щось із нуля.

**Наступний крок:** дочекатись рішення користувача щодо якості 8x8/6x8 (прийнятно як є, чи пробувати
покращити конкретні літери), потім писати сам код — `HX8353E_charset_UA.h`, `ukrainian.h`,
`LANGUAGE_BUILD_UKRAINIAN` у Makefile, реєстрацію нової мови в `languages[]`.
